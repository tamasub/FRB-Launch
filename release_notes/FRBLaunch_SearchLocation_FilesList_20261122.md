# FRB Launch — 検索結果の Files List 共通化／Search Location 試作

## 適用元
`launch_app_20261122_184811.zip`。差分ZIPをバックアップ済みの同じフォルダーへ展開・上書きする。

## 変更内容

1. **DATA / VIEW / ACTION の分離を保った検索表示**
   - 検索エンジンと検索結果生成は既存 `app.render()` の結果を再利用する。
   - 検索結果（行・階層情報）を `location_model.search_list_rows()` で Files List と同じ行データへ投影する。
   - Files List 本体の `fill`、選択、プレビュー、対象別コンテキスト操作を再利用する。
   - 検索時のみ列表示を `タイトル／説明・場所／項目の種類` へ切り替える。
   - 検索一覧に「（カレントフォルダー）」は付けない。検索結果欄内の絞り込みは従来の List 検索を利用する。

2. **Search Location とパンくず**
   - `🔍 検索結果：検索語` を単独の表示 Location とする。物理・JSON の偽の親フォルダーを作らない。
   - 検索結果の各行は本来のファイルパスまたは JSON アイテムの識別子を維持する。
   - 検索結果でフォルダーを開いて初めて、その実体 Location に移る。

3. **時系列のナビゲーション履歴**
   - 既存の Files フォルダー履歴に Search Location を加え、戻る／進むから復元可能にする。
   - 検索文字を入力するたびに履歴が増えないよう、連続する検索編集は同一履歴項目を更新する。
   - 戻ってきた検索結果の選択行・スクロール位置の復元を試みる。選択位置の記録だけでは「進む」履歴を破棄しない。
   - **検索キーワード履歴とは別**。ファイルの実行・プレビューでも移動履歴を追加しない。

4. **既存 ACTION の再利用**
   - ファイルの既存プレビュー経路を利用（実際の第三列表示はOS・アプリ設定に依存）。
   - フォルダーの内部移動、選択行を起点とする Keyboard EX、対象別の右クリックを既存処理に接続。
   - Search Location 自体には共通のカレントフォルダーがないので、背景での貼付け・背景コンテキストを抑止。

5. **JSON選択型は従来どおり**
   - Mailなどのチェック選択に入ったら旧選択一覧・F12送信へ接続する。
   - 選択型に新しい右クリックメニューは作らない。
   - Space複数選択、ファイル／URL一括操作、F12汎用化は今回対象外。

## テスト結果
- 変更Pythonの `py_compile` 通過。
- 9つの関連テストモジュール: **58 passed, 3 skipped, 1 deselected**。
- `deselected` は変更対象でない `app.execute` の単体抜粋テスト。テスト用の部分オブジェクトに既存 `_resolve_registered_shell_shortcut` がないことで失敗したため、今回の検証対象から外した。
- **Windows GUI 実機テストは未実施**（この環境にはPySide6/Windowsがない）。データと操作の静的／ヘッドレス検証結果であり、動作を保証するものではない。

## Windows実機で確認してほしい手順
1. Filesモードの検索欄に `佐藤` 等を入力 → 同じ Files List に結果が出るか。ヘッダーが検索用に変わり、（カレントフォルダー）行がないか。
2. `.md` ファイルの検索結果をダブルクリック → 既存Files Listと同じ外部エディター／第3列表示設定に従うか。右クリックにファイルメニューが出るか。
3. フォルダーの検索結果を選んで Menu キー → 対象フォルダー起点のKeyboard EXか。そのフォルダーを開くと正しいパンくずへ移るか。
4. `My Work → 検索結果 → 実フォルダー` を往復して、戻る・進むで検索条件と選択位置が復元されるか。
5. Mail選択型行をチェック → 従来の選択モード、対象絞り込み、F12送信が使えるか。右クリックメニューは追加していない。
6. 検索欄を空に戻す → 元のFiles List/フォルダー階層が復元されるか。
7. フォルダー内の絞り込み・通常Files List操作・Browser表示に回帰がないか。
