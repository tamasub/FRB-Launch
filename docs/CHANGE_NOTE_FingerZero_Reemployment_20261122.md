# FRB Launch — 小指Zeroの逆襲（2026-11-22）

## 今回の人事異動

| 物理キー | 対象局面 | 既存操作への接続 |
| --- | --- | --- |
| テンキー0 | Exp／List／コンテキストメニュー／非入力ダイアログ | Enter（フォルダー展開、ファイル実行、選択実行、ダイアログ確定） |
| テンキー1 | Launch配下のQDialog | Tab（次の入力項目・ボタンへフォーカス） |
| Windows メニューキー | Launch配下の画面（主にFiles） | 既存の `/`（Exp Keyboard Exの表示・閉じる） |

- **本物のEnter、Tab、`/`、矢印キーの定義は変更しない。**
- テンキーの **0/1** を認識する。メイン数字段の0/1、独立したInsert/Endは置き換えない。
- NumLockはプログラムから変更しない。NumLock ON（0/1）と、Qtがテンキーとして識別できるOFF（Insert/End）の両方を扱う。
- テンキー0はテキスト／数値入力・インラインリネーム中には割り込まず、文字の0として使える。
- テンキー1は**ダイアログ内ではTab優先**。ダイアログの入力欄で数字の「1」を入力する際は、メイン数字段の1を使う（テンキー1は項目送り）。ダイアログ外は従来どおり。
- メニューキーは、従来明示的に無効化されていたルートを解除し、Launchで既に存在する `/` ナビゲーション関数に接続。ネイティブのキーボード起点ContextMenuイベントだけが来るWindows環境にも対応し、KeyPressと両方来ても二重トグルしない。
- テンキー0/1はShift/Ctrl/Altとの複合キーでは割り当てない。
- 既存の「ListでInsert→現在のフォルダー」や「Listで→→コンテキストメニュー」は変更しない。
- Qtアプリケーション全体のイベントフィルタを利用するが、対象は **Launcherが所有するウィジェットのみ**。外部アプリのキーは変更しない。

## 差分

- `src/finger_zero_keys.py`：Qtに依存しない物理テンキー判定（新規）
- `src/expanded_view.py`：入力判定、KeyPress/KeyReleaseの振り分け、既存Enter/Tab/Slashへの委譲
- `tests/test_finger_zero_20261122.py`：0/1/メニューキーの物理キー判定テスト（新規）
- `tests/test_finger_zero_ui_bridge_20261122.py`：既存イベントへの委譲テスト（新規）
- `tests/test_insert_current_folder_menu_disabled_20261121.py`：過去の「Menuは無効」というテスト想定を今回の再任用仕様へ更新

## 検証

- 37件 PASS：上記追加・関連のキー判定、Menu経路、Insert動作、旧`/`経路など（PySide6不使用のテスト）
- `compileall` PASS：変更したPythonソース
- Windows上の**実キー操作**は、このLinux実行環境では未確認。NumLock OFFのテンキーがQtの `KeypadModifier` を伴うかを実機で確認すること。
- 参考：古い `test_expanded_keyboard_dispatch_20261024.py` に、現行UIへの追従不足によるテストダブルの属性不足で4件失敗あり。今回未変更の `src/app.py` を直接呼ぶテストであり、本改修による回帰判定には用いない。

## Windows実機確認の順番

1. 普通の矢印キーでExp/Listを選択し、テンキー0でフォルダー展開・ファイル実行。
2. コンテキストメニューの選択項目をテンキー0で確定。
3. ダイアログの入力欄やボタンでテンキー1→Tab移動、テンキー0→非入力欄からEnter実行。
4. メニューキーで`/`と同じExp Keyboard Exを開き、もう一度押して閉じる。
5. 入力欄のテンキー0、メイン数字段0/1、独立Insert/End、通常の矢印／Enter／Tab／`/`が変わっていないことを確認。
6. NumLockを切り替えて0/1の物理キー判定を確認（常用する設定を変更する必要はない）。
